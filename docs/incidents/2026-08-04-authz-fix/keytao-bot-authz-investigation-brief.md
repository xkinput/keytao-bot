# keytao-bot 安全拦截逻辑排查简报

## 背景

keytao-bot 是 QQ 群里的键道输入法词库助手（仓库：`/Users/rea/code/keytao-org/keytao-bot`）。
群友「朝歌」请求把「吃席」调到「赤溪」的码位（调码顺延），bot 连续 6+ 次以「安全拦截」为由拒绝执行，
每次给出的补救指令格式都不同，用户逐条照做仍然被拦，最终用户放弃（回复「......」）。

项目负责人（rea）的判断：**不应存在反复的安全拦截。用户已明确确认的顺延调码应直接执行；
可做即做，有未知问题直接告知用户，而不是让用户反复换格式重发指令。**

## 任务（仅诊断，不改代码）

1. 通读授权/拦截相关代码路径，对下面每一次拦截给出根因定位（file:line 级别）。
2. 识别设计层面的缺陷（不只是单点 bug），例如：
   - 拦截判定读的是「渲染后注入了记忆/上下文块的消息」还是「用户原始文本」？
   - 待执行操作（pending plan）与用户确认之间如何绑定？每轮是否重新生成 plan 导致确认永远失配？
   - 「引用消息不可授权」的判定是否把 QQ 的 @ 回复/普通消息误判为引用？
   - 「确认票据 070062」机制是什么、为何出现后又没用上？
3. 检查撤回/批次状态机：撤回提审后词条为何没回到草稿（出现了两个批次 ID：
   `785e0368` 和 `ec511ac6`，撤回后草稿 0 条，「吃席」既不在词库也不在草稿）。
4. 对照现有测试（`test_security_fixes.py`、`test_memory_safety.py`、`test_review_gate.py`、
   `test_state_machine.py`、`test_llm_policy.py` 等）说明这些拦截行为哪些是测试固化的「有意设计」、
   哪些是实现走样。
5. 给出具体修复建议（方案级，含涉及文件和改动思路），使行为符合负责人预期：
   - 用户的明确当前指令（含 @bot 的普通群消息）应能一次性授权执行；
   - 安全校验失败时最多提示一次、且提示的补救方式必须真实有效；
   - 状态机不应把词条弄丢。
