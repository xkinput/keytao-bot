# 喵喵语义路由重构方案（2026-10-14）

## 现状

- 每条消息先过一长串固定句式与待选候选的优先认领（`chat_routing._classify_message_command_intent`），全部没命中才调用意图模型（`WORD_QUERY_INTENT_MODEL`，线上为 glm-5.3）。
- 意图模型的 intent 枚举只覆盖草稿管理与 pending_*；对调、删词、改码、调序、移动这类写操作只能由正则（`authorization_grammar.py`，5792 行）识别。
- 写操作的授权（`message_authorizes_mutation` / `tools._validate_policy`）同样基于正则：一句话不在句式表里，即使主模型理解了，也写不进去。
- 结果：每出现一种新说法就要补一次正则；另外待选候选按「消息以候选词开头」之类的启发式规则认领消息，会把无关的新指令吞掉（2026-10-14「调整调换 午时 和 务实 词条」两次失败）。
- 线上调用量：72 小时内 47 次 command_intent，每次约 800–1000 tokens，其中约 576 tokens 命中缓存。

## 目标

模型负责「理解用户想做什么」，代码负责「校验能不能做」，用户确认负责「授权写入」。

## 关键设计决定

1. **统一操作表示**：所有入口产出同一个 `OperationRequest {op, operands[], codes[], submit_after, refers_to_pending}`。
2. **理解顺序**：精确命中封闭句式 → 走快速通道（省一次模型调用）；否则调用一次语义解析模型，用 JSON schema 输出 `OperationRequest`。
3. **待选候选的认领交给模型判断**：由 `refers_to_pending` 字段决定，校验器要求操作对象确实属于这条候选记录。删除「消息以候选词开头即认领」这类启发式规则。
4. **硬校验（fail-closed）**：
   - 操作对象必须在用户原话中逐字出现（或属于本人的有效候选记录）。
   - 现有的引用、转述、问句、否定守卫原样保留。
   - 词库记录必须唯一，服务端继续做 CAS 校验。
   - 模型出错、超时或返回非法 JSON 时：退回现有行为，绝不写入。
   - 像查词的消息一律按查词处理（吸取 S70 的教训：模型给出「无意图」时不能吞掉查词请求）。
5. **授权口径**：
   - 模型理解出来的写操作一律先给出方案，同一用户确认后才写入（沿用现有的封存票据和 CAS）。
   - 一句话直接写入只保留给封闭句式和喵喵自己提示过的指令格式（如「调整调换 tqdh，加入」）。

### 2026-10-15 B2 结论与安全口径

- 安全边界是「消息作者本人确认」，不是 frame 判断：B3 起，模型理解出来的写操作无论 frame 是什么，都必须由发消息的本人确认已封存的方案后才写入。frame 只决定「直接出方案」还是「先回答问题」。
- `validate_operation` 里的 frame 兜底（问句、否定、引用+评论、转述）只做纵深防御，只降级不升级；不再为转述、撤回等说法追加正则（Opus 第二轮评审列出的 7 类绕过中，只修了问句标记、常见问法、引号样式和「嘛/呢」误拦）。
- glm-5.3 真实测评（第二次，654 条，拆掉 `{"answer": ...}` 包装后）：危险误判 0、查词误当写操作 0、正常指令误降级 0；对调 95%、删词 96%、改码 95%、调序 100%、加词 92%、移动 72%、查词 95%、确认 87%、选码 90%、frame 97%、回应候选判断 98%。模型判对而正则判错 510 条，反之 3 条。两次测评合计约 130 万 tokens。
- 已知弱项：help 1/8、chat 65%（不涉及写操作）。

## 成本

- 线上：消息量很小（约 16 次/天走意图模型）。B2 用一次语义解析替换现有意图调用，单次 tokens 预计从约 1k 涨到约 2–3k（提示词变长，大部分可缓存）。
- 验收：测评集真实模型跑一遍 ≈ 300 条 × 约 3k tokens ≈ 90 万 tokens（大部分为缓存命中），只跑一次；跑之前先报人民币金额并取得授权（本地没有价格表，需确认 glm-5.3 单价）。

## 代价与风险

- 自由说法的写操作会多一轮确认；习惯「一句话直接写」的用户需要回复一次「确认」。
- 没命中快速通道的消息多约 1–2 秒模型延迟（今天这些消息本来就会调用意图模型，增量有限）。
- B3 改变授权口径，属于安全相关改动，必须单独评审。
